# Security boundary

Hiraishi trusts pi, selected extensions, its own host-side controller and Anthropic Sandbox Runtime 0.0.81. It confines read/write/edit/bash, their descendants and user shell commands on Linux. Other extension internals, resource discovery, model/provider access and `pi.exec` remain trusted host operations. A malicious same-process extension is outside the boundary. Do not install the runtime or configuration under a writable grant.

SRT is the only OS/network isolation backend. There is no classifier, confidence threshold or command allowlist. Parent tools retain human-controlled session permissions; subagent grants are selected explicitly as described below. Invalid settings, missing dependencies, startup errors and unsupported platforms leave the guarded tools unavailable. They never restore pi's local operations.

## Files and environment

A root read deny re-exposes system runtimes, SRT's native helpers, explicit read grants, the workspace and dedicated temporary/HOME directories. Only SRT's own proxy endpoints and public CA/trust files are re-exposed as required by its implementation. Its private CA key remains hidden. Write access is limited to the workspace and configured grants. User grants cannot overlap private SRT session state. HOME and its ancestors cannot be read roots; pi state directories cannot be whole read roots or overlap write roots, including a custom active agent directory. The host's shared `/tmp/claude` convenience directory is explicitly denied as well as the general shared `/tmp` contents.

Host credentials and shell startup variables are not inherited by the runner. It starts with a small environment; sandbox commands receive a fresh HOME and TMPDIR. Runtime lookup excludes writable PATH directories. Known credential locations and pi auth/models files and session histories are denied, but allowed projects, references and caches can contain other secrets. There is no content-based secret filter. Reads may be forwarded to the selected model provider; tools may transmit allowed files over permitted HTTP requests.

Mounted write grants modify host data. They do not create snapshots, protect uncommitted work within those grants, or make Git tracking equivalent to recovery. Use a separate copy if losing workspace files is unacceptable. Existing hard links and other shared writable aliases can also connect files across apparent paths; grant only directories whose contents may be modified. Kernel vulnerabilities and malicious host processes with the same uid are outside this boundary.

## Network

The tool network namespace has no direct external connection. SRT's authenticated relay proxies mediate HTTP and HTTPS. SRT's own local relay sockets are usable by its pre-seccomp infrastructure, while workloads cannot create arbitrary Unix/vsock sockets. `refuseOpaqueTunnels`, TLS termination, host consistency checks and a per-request method filter are enabled together. TLS exclusions, upstream proxies and weakened SRT isolation are not exposed as user options.

Domain permission uses SRT's callback, deterministically derived from the session mode; it never opens a per-domain approval prompt. Literal IPs and localhost names are refused by this callback because SRT's DNS guard intentionally exempts those cases. Remaining hostnames use SRT's single-resolution address guard with explicit private/non-public ranges. This is not an assertion that every network deployment (for example a public address routing into private infrastructure) is distinguishable as private.

`off`, `http-get` and `http-all` describe HTTP capabilities, not user intent. GET and HEAD can disclose data in URLs or trigger mutations. All-method mode permits uploads and anonymous remote updates. A model error within those permissions can have external effects. No host service credential is automatically made available. Authenticated publication/deployment requires a separate explicit design or human execution.

## Sessions and teardown

A command-line `--hiraishi-grants` JSON selects session permissions at process start. It is validated like config entries except that `socatPath`, `hostCommands`, `maxReadOnly` and `maxReadWrite` are rejected, so a caller can never add host-side commands or a ceiling of its own. Directory grants are additive to the config file unless the request names them in `replace`, and `denyRead` only grows through union. An explicit grant `maxNetworkMode`, else `networkMode`, caps the session; a value above the configured `maxNetworkMode` needs an explicit user approval, and the approved value then becomes the ceiling. Configured `maxReadOnly` and `maxReadWrite` entries grant nothing by themselves; they widen only the path ceiling that a command-line request, a subagent grant or a host `{cwd}` may reach without a dialog. `maxReadWrite` belongs to both the read and write ceiling. Choosing the baseline option drops the requested additions but keeps the restrictions the same request carried (added `denyRead`, `noHostCommands`, `replace` narrowing, a lower ceiling). Requests that are refused or malformed with no dialog available end the process with a stderr message; other startup failures leave the session with tools unavailable. Paths, including the workspace, are canonicalized when loaded and merged, and every policy rebuild refuses a path that no longer resolves to itself, which bounds a later symlink swap. The resolved permissions become the session ceiling for `/hiraishi-network`, subagents and host commands. Runtime protection rules (HOME, pi state, session internals, credential paths) still apply to any granted path.

Each active parent session and each subagent invocation owns a separate runner process and SRT instance. Subagents start with network off and no extra read/write grants; parent network changes and configured positive grants are not inherited. Configured read denies and runtime protection rules remain enforced. The parent can supply explicit child-only network and directory grants. Network grants may reach the session ceiling; directory grants must stay inside the session path ceiling (configured grants plus `maxReadOnly` and `maxReadWrite`), so a child cannot receive a path the session itself could not request. This makes the parent model a trusted permission decision maker within the user's authorized task. Instructions require user selection when authorization is uncertain; this judgment is not an independent policy classifier. Grants beyond the ceiling fail closed unless `approval: "user"` is set, and such requests cannot proceed without a user choice; cancel or dismissal does not open a sandbox. Each grant lasts one invocation; children cannot grant permissions or delegate recursively.

## Host commands

`hostCommands` in the configuration declares host programs that run outside the sandbox on the model's behalf. This is trusted host code, comparable to `pi.exec`: the model selects a configured operation, never the binary, the flags or a shell. Argument templates are fixed by the operator, each placeholder must fill a whole argv entry, and values are substituted only after validation: `{cwd}` must be an existing directory inside the session workspace, a write grant or the configured `maxReadWrite` ceiling; any other directory requires an interactive user confirmation that shows the command, operation, resolved path, child grants and task opening with control characters neutralized, and is refused when no UI is available. A child workspace is writable, so a read-only path outside the write ceiling cannot be one. `{task}` may not begin with `-` or `@`, which the started program would read as an option or a file argument. `{grants}` is required on the starting operation and on any operation that starts `{hiraishi}`, and it is always rewritten: requested paths are intersected with the configuration baseline, baseline entries that the session still allows are passed as an exact `replace` set, both network values are capped at the session ceiling, the session `denyRead` is unioned in, the expected workspace is pinned as `cwd` for the child to verify, and `noHostCommands` stops a delegated child from delegating further. A delegated child never receives `maxReadOnly` or `maxReadWrite`, so its own configuration cannot widen the grants the parent passed. This keeps a host-launched child inside the session even when the caller used `replace` or supplied no grants. A command whose path resolves inside a writable grant is refused; operations that take `{name}` reach only children started by the same command in the same session. Session changes and cancellation abort the host call, but only the direct host process: a background child started by that program survives and is no longer controllable. An operation that starts the host `pi` without `{hiraishi}` runs it outside Hiraishi; the operator is responsible for such templates. A command entry may name additional environment variables in `env`, which extend the fixed host environment for that command only. Names are validated at configuration load as `[A-Za-z_][A-Za-z0-9_]*`, and a value is copied only when the host `pi` process has it. `env` is configuration-only and cannot be supplied through `--hiraishi-grants`. Passed values are ordinary process environment for a trusted host command: credentials, socket paths and similar inherited authority become available to that command, so the operator must declare only trusted programs and the minimum set of variables they need.

Nested operations still pass through pi's tool hooks and validation; an asynchronous scope routes Hiraishi's adapters to the child's SRT instance rather than the parent's. Cancellation and completion tear down child runners. Parent lifecycle changes and network changes stop active child sandboxes too. Cleanup failure remains observable and blocks normal parent replacement. Model selection is independent of tool permissions: any registered pi chat model can be selected through the host model registry, with no Hiraishi provider allowlist or credential forwarding to the runner.

Permission transitions stop new admissions synchronously, invalidate the generation, reject pending calls and terminate tracked tool process groups. The old runner shuts down SRT before a replacement starts. Runner exit also triggers host-side termination of known tool groups and relay processes. Shutdown interrupts startup and permission changes, and concurrent stops share completion. Extension lifecycle changes clear the active reference before awaiting teardown; new starts wait for cleanup. Cleanup failure blocks replacement; fatal errors trigger teardown. There is no replay queue.

Each tool's operations capture their starting generation. An edit that read under an old generation cannot write after a permission transition. Shutdown or mode changes cannot retract bytes already sent or roll back completed mutations. Commands and their descendants are terminated when a tool finishes; persistent background tasks are unsupported. There are time and per-file limits but no CPU, memory or disk quotas.

Filesystem permission semantics and TLS termination are SRT functionality and must be rechecked on upgrades. The exact dependency is pinned. Integration tests verify boundaries and failure behavior with synthetic local files and services; they are not a proof against all OS/runtime vulnerabilities.

## Dependency advisories

The 2026-11-02 `npm audit` check reports five affected packages (three high, two moderate), including SRT through zod and the pi peer through undici/minimatch. npm supplies no compatible automatic fix. Hiraishi bounds its own configuration collections and accepts them only from trusted personal settings, but this does not establish that every upstream advisory is unreachable. The pi provider/network stack remains trusted host code. Track upstream fixes and repeat this check when updating the pinned runtime or supported pi version.
